LLM 不是 Agent：先理解模型、推理与生成

发表于 2026-08-04 分类于 AI Waline：
这篇文章拆开 LLM、模型服务和 Agent 系统各自负责什么，也解释一次 Inference 如何生成结果。文末用一轮禁止工具调用的技术调研做实验：模型能给出完整答案，却无法确认资料是否最新，也不能自己搜索、保存进度或验收结果。

LLM 不是 Agent：先理解模型、推理与生成

在聊天窗口里输入一句话，模型能分析需求、列计划、写代码。接上搜索和文件工具后，它还会查资料、改文件。用户看到的只有同一个输入框，很容易把背后的所有能力都算到 LLM 头上。

可如果程序在模型返回第一条结果后就停止，任务也会停在那里。工具不会自己执行，任务进度没人保存，结果也没人检查。模型只是完成了一次生成。

我更愿意把 LLM 看成 Agent 系统里的“决策部件”。它很重要，却不是整台机器。

先把三层拆开

我们平时使用的聊天产品，已经把对话历史、文件解析、搜索、代码执行和安全检查包在了一起。界面很简单，组件之间的分工却被藏了起来。

把它们拆开，大致是三层：

层次 做什么 输入 输出
模型 根据当前内容继续生成 Token 序列 新 Token 或结构化结果
模型服务 提供模型调用接口 Request Response、用量、结束状态
Agent 系统 管理任务、工具、状态和权限 用户目标、环境状态 任务结果、执行记录

模型服务和 Agent 系统可能由同一家产品提供，代码里甚至只需要调用一个 SDK。不过，状态仍要保存，工具仍要执行，失败也仍要处理，只是这些工作被产品包装了起来。

LLM 在一次调用里做了什么

主流 LLM 大多建立在 Transformer 及其后续架构上。生成文本时，模型根据当前 Token 计算下一个 Token 的概率分布，选出一个结果，再继续往后生成。

已有 Token
   ↓
计算下一个 Token 的概率
   ↓
选择并追加 Token
   ↓
继续，直到停止

这段计算叫 Inference，中文通常译作“推理”。它指模型接收输入并完成计算，不代表用户交代的事情已经办完。

例如输入：

请比较三个 Agent Runtime。

模型会根据当前上下文和训练得到的参数生成回答。它不会自动创建研究项目，也不会花几个小时阅读官网后再带着核验过的资料回来。要完成这些动作，外部系统必须提供工具，并在第一次生成结束后继续驱动任务。

同一份输入也未必得到相同结果。模型计算出的是概率分布，解码时可以选择最高概率项，也可以从候选项中采样。Temperature、top-p 等参数会改变选择范围。Temperature 升高后，低概率候选通常更容易出现，输出可能更丰富，也可能跑偏。因此，把 Temperature 简单理解成“创造力旋钮”并不准确。

模型返回的是生成结果，不是已经验收的事实。内容是否真实、能不能满足业务要求，还得另外检查。

模型没有一直守着任务

一次 Inference 结束后，模型的计算就结束了。下一次调用能看到什么，由应用提交的输入决定。某些服务可以通过会话 ID 续接历史，但任务计划、预算、审批状态和中间文件仍要有人管理。

产品可以通过数据库或服务端会话记住上次聊天，但这不等于模型自己保存着任务。裸模型没有这样的业务状态。

拿调研任务来说，模型可以写出“下一步应该查官方文档”，但这句话不会给它变出浏览器，页面也不会自己打开。要把建议变成动作，还缺少这些条件：

  • 可以操作的工具和环境；
  • 当前做到哪里的状态记录；
  • 判断完成与失败的规则；
  • 对写文件、发消息等动作的权限。

模型写出了动作，Runtime 才负责执行。这是两步。

什么时候才开始像 Agent

回复次数不能用来判断系统是不是 Agent。连续聊十轮，有可能只是应用反复把旧消息交给模型。

当系统开始根据模型结果采取行动，再把环境返回的结果交给模型时，才出现 Agent Loop：

任务
  ↓
模型决定下一步
  ↓
系统执行工具
  ↓
环境返回结果
  ↓
更新状态
  ↓
继续或结束

模型判断下一步做什么，外部程序执行动作，并决定是否继续循环。后面的文章会分别讨论 Tool Calling、State 和 Runtime，这里先把这层分工说清楚。

更强的模型也救不了坏掉的系统

即使模型正确判断出“应该先看官方文档”，系统仍然可能出错。

系统可能根本没有搜索工具，也可能读到过期页面。工具超时后如果只会反复重试，费用会继续增加；没有验收规则时，缺少引用的报告也可能被直接交付。换一个参数更多的模型，解决不了这些故障。

问题 主要由谁负责
理解要求、提出下一步 模型
获取网页、文件和数据库内容 工具与环境
保存进度、处理超时和恢复 Runtime
判断结果能否交付 验收规则与权限系统

模型能力会影响 Agent 能做什么，但任务能否稳定完成，还取决于模型之外的系统。

C01：让裸模型做一次技术调研

这个系列会逐步实现一个“技术调研与报告交付 Agent”。在 C01 中，我先关闭搜索，不保存任务状态，也不验证结果，只发出下面这条请求：

调研三个主流 Agent Runtime，比较它们的状态管理、持久化、人工审批和可观测性，并给出选型建议。

模型确实给出了一篇结构完整的答案，比较维度看起来也合理。但只看这份输出，我无法确认：

  • 它依据的是哪一版资料？
  • 关键结论来自哪里？
  • 它有没有读过当前官方文档？
  • 信息不够时，谁负责继续调查？
  • “调研完成”由谁判断？

一次模型调用回答不了这些问题。

C01 的能力缺口

调研要求 裸模型能做什么 还缺什么
理解主题 提炼比较维度 明确的任务范围和验收条件
获取当前资料 根据训练参数生成内容 搜索、读取工具
记录证据 在文本里写引用 可追踪的证据存储
持续推进 描述后续计划 循环和任务状态
交付报告 生成正文 文件写入、验证和发布权限

这次实验里，模型已经表现出不错的问题整理和内容生成能力。C01 关心的是另一件事：它给出一次回答后，系统还要补上哪些部件，才能把调研真正做完。

几个容易混淆的地方

多轮聊天最容易被误认成 Agent。应用可能只是反复提交历史消息，既没有工具，也没有独立的任务状态。

Tool Call 则是一份调用请求。模型生成函数名和参数后，网络请求、数据库查询或文件写入仍由 Runtime 完成。

长 Context 只说明模型这次能读取更多内容。信息是否长期保存、何时更新或删除，属于 Memory 的设计。

计划同样可能只是一段文本。模型写下“先搜索，再比较，最后写报告”之后，仍要由工具执行步骤，由状态记录进度，并由 Runtime 判断何时停止。

小结

LLM 读取当前上下文，完成一次 Inference，然后返回结果。模型服务承载这次调用。接下来，Agent 系统还要执行工具、保存进度、处理权限，并判断任务是否结束。

后面讨论 Agent Loop 时还会反复遇到这条边界：模型给出下一步，Runtime 执行动作，并处理动作对真实环境造成的影响。

案例实践

  • 使用不带搜索和工具的模型执行 C01 提示。
  • 保存输入、模型标识、参数、调用时间和原始输出。
  • 标出回答里的实时事实、无来源主张和无法核验的结论。
  • 按“任务、工具、证据、状态、验收”整理能力缺口。
  • 确认聊天产品没有在后台启用搜索或文件工具。
